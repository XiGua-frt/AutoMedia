# `image_search_service.py` 图片服务层说明

## 文件主要作用

`python-backend/app/services/image_search_service.py` 定义了一个抽象基类 `ImageSearchService`，它不是具体的“某个图片服务实现”，而是整个图片能力的**统一接口层（抽象层）**。

一句话定位：**把“如何拿图”这件事抽象成统一协议，让 Pexels、NanoBanana、Mermaid、Iconify 等不同来源都能按同一种方式被调用。**

---

## 这个抽象层解决了什么问题

- **统一调用方式**：上层只调用 `get_image()` / `get_image_data()`，不关心底层是图库检索还是 AI 生图
- **参数选择标准化**：通过 `request.get_effective_param(self.get_method().is_ai_generated())` 自动决定传 `keywords` 还是 `prompt`
- **扩展成本低**：新增图片来源时只要继承 `ImageSearchService` 并实现 3 个抽象方法
- **降级能力约束**：每个实现都必须提供 `get_fallback_image()`，保证失败时可兜底
- **健康检查入口**：`is_available()` 允许子类重写，便于运行时熔断/跳过不可用服务

---

## 类结构与关键方法

`ImageSearchService` 的核心设计是 “模板方法 + 抽象方法”：

- `get_image(request)`：模板方法（已实现）
  - 自动判断当前服务是否 AI 生图
  - 自动从 `ImageRequest` 提取最合适参数
  - 统一调用子类实现的 `search_image(param)`
- `get_image_data(request)`：模板方法（已实现）
  - 默认先拿 URL，再转为 `ImageData`
  - 子类可重写为更高效数据通道（如直接返回 bytes）
- `search_image(keywords)`：抽象方法（必须实现）
  - 真正执行“查图/生图”逻辑
- `get_method()`：抽象方法（必须实现）
  - 声明该服务对应的 `ImageMethodEnum`
- `get_fallback_image(position)`：抽象方法（必须实现）
  - 声明该服务兜底图片策略
- `is_available()`：可选重写
  - 默认 `True`，子类可做配置检测、健康检查

## 调用链路图（Mermaid）

### 图1：抽象接口层调用链（`ImageSearchService` 内部）

```mermaid
flowchart TD
    A[上层传入 ImageRequest] --> B[get_image(request)]
    B --> C[get_method]
    C --> D[is_ai_generated]
    D --> E[request.get_effective_param(is_ai)]
    E --> F[search_image(param)\n由子类实现]
    F --> G[返回图片 URL 或 None]

    A --> H[get_image_data(request)]
    H --> I[get_image(request)]
    I --> J[ImageData.from_url(url)]
    J --> K[返回 ImageData]
```

说明：  
`get_image()` 和 `get_image_data()` 是统一入口，真正差异化逻辑由各子类在 `search_image()` 中实现。

---

### 图2：在项目中的实际业务调用链

```mermaid
flowchart TD
    A[ArticleAgentService.agent5_generate_images] --> B[ParallelImageGenerator.generate]
    B --> C[ImageServiceStrategy.get_image_and_upload]
    C --> D[_resolve_method(imageSource)]
    D --> E[service_map[method]\n拿到具体服务实例]
    E --> F[具体服务.get_image_data(request)]
    F --> G[ImageSearchService.get_image_data\n默认实现]
    G --> H[get_image(request)]
    H --> I[search_image(param)\nPexels/NanoBanana/Mermaid...]
    I --> J[返回 URL 或 bytes 封装为 ImageData]
    J --> K[CosService.upload_image_data]
    K --> L[返回 COS URL]
    L --> M[写回 state.images 并 SSE 推送 IMAGE_COMPLETE]

    E -.服务不可用/失败.-> N[_handle_fallback_with_upload]
    N --> O[get_fallback_image(position)]
    O --> K
```

说明：  
`image_search_service.py` 处于图中的“协议层”，`image_service_strategy.py` 负责“运行时选择哪个协议实现”。

---

## 为什么这是关键层

- 它让图片系统具备了**插件化能力**：新增服务（如 Unsplash）不改上层流程
- 它让参数选择逻辑从业务层剥离，避免到处写 `if method == ...`
- 它和策略层配合，形成清晰分工：  
  - `ImageSearchService`：定义“服务该怎么实现”  
  - `ImageServiceStrategy`：决定“当前用哪个实现 + 失败怎么降级 + 统一上传 COS”

---

## 一句话总结

`image_search_service.py` 是图片服务体系的**抽象契约层**：统一入参、统一输出、统一扩展点，为上层 Agent 工作流屏蔽多来源图片实现差异。
